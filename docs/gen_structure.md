# EWT generator structure

Companion to [`coverage.md`](coverage.md). Where `coverage.md` answers _which
Flutter widgets are supported_, this file answers _how the Java surface is
laid out_, _how the generator itself is organised_, and _which shapes the
generator still can't handle_.

## 1. Hand-written vs. generated Java

Every `.java` file in `ewt.api/src/main/java/dev/equo/ewt/` and its
subpackages falls into one of four buckets.

### 1a. Generated on every `:generator:generator` run

**Path:** `ewt.api/src/main/java/dev/equo/ewt/*.java` (top-level only).

For each entry in `generator/lib/generation_index.dart`, the generator emits:

- `<Widget>.java` — concrete class + Immutables `@Builder.Factory`.
- `<Widget>I.java` — the builder interface consumed by other generated
  widgets' typed params.

Also generated top-level: enums declared inside Flutter widget libraries
(`BlendMode.java`, `Clip.java`, `DatePickerEntryMode.java`, …).

Two aggregate files are re-written each run:

- `EWT.java` — the static-factory facade (`EWT.DataTable(...)`,
  `EWT.showDatePicker(...)`, …).
- `WidgetConstructors.java` — the FFM dispatch table Java calls into.

Per-widget outputs are **tracked** (committed) so reviewers can see the byte
diff a generator change produces. The aggregate files above are also tracked.

### 1b. Generated by `:ewt.api:jextract`

**Path:** `ewt.api/src/main/java/dev/equo/ewt/ffm/` (entire subpackage).

**Gitignored** (see `.gitignore` line for `ewt.api/src/main/java/dev/equo/ewt/ffm/`).
Jextract produces one Java class per C struct / function pointer declared in
`widgets/src/Starter.h` (which is itself regenerated). Never edit — these
files are recreated from scratch on each build.

### 1c. Hand-written support (top-level `dev/equo/ewt/`)

These files are checked in and never overwritten by the generator. They
implement the base classes and mixins the generated widgets depend on:

| File | Role |
|---|---|
| `App.java` | Entry point (`App.runApp(...)`), native library loader, FFM arena. |
| `NativeObj.java` | Opaque native handle — the `int id` that survives the Java↔Dart boundary. Provides `NativeObj.Base` used by every `EWT.*` value type. |
| `Widget.java`, `StatefulWidget.java`, `StatelessWidget.java`, `State.java` | Flutter-analog base classes for user code. |
| `SubStatefulWidget.java`, `SubStatelessWidget.java`, `SubState.java`, `SubAnimatedState.java` | EWT subclass-in-Java pattern — the four classes users extend to build custom widgets with Java-side overrides. |
| `SubclassedInJava.java` | Marker interface consumed by the generator's `SubclassGen` code path — routing lives in `Types.getGen` (see §2b). |
| `BuildContext.java` | Small interface wrapper around the generated `BuildContextI`. |
| `WidgetConstructorsBase.java` | Base class extended by the generated `WidgetConstructors` — holds the `factories` field and other cross-widget statics. |
| `SerializingWidgetConstructors.java` | Web-transport equivalent of `WidgetConstructors`; serializes widget calls into a JSON message the web runtime replays. |
| `EwtCapture.java`, `EwtWebCapture.java`, `EwtWebState.java`, `EWTStyle.java` | Web-integration helpers used from the web transport path. |
| `NativeLibLoader.java` | Picks the correct native library set per-OS / per-mode (standalone vs. Evolve attach). |
| `Colors.java`, `Curves.java`, `Icons.java`, `CupertinoIcons.java`, `Durations.java` | Static constant holders — the generator emits these as pass-through wrappers, but the constant tables themselves are curated. |

If you touch anything in this list, remember to regenerate afterwards
because the generator's output depends on their signatures being stable.

### 1d. Hand-written subpackages

Fully hand-written; never touched by the generator.

| Package | Contents |
|---|---|
| `dev/equo/ewt/util/` | `Tri*`/`Quad*`/`Penta*` `Function`/`Consumer` interfaces — arity extensions beyond `java.util.function.BiFunction`. Consumed by generated code (e.g., `PentaFunction` is what `Hero.flightShuttleBuilder` compiles to). |
| `dev/equo/ewt/internal/` | `EmbedBridge` (EWT↔Evolve same-surface integration), `HotReloadRoot` (JDWP-triggered `reassembleApplication` wrapper). |
| `dev/equo/ewt/web/` | Web-transport plumbing: `EwtWebTransport`, `EwtNode`, `EwtNodeJson`, `EwtDiff`, `Patch`, `SetParamsOp`. Reads/writes the JSON diff protocol used by `widgets_web`. |
| `dev/equo/ewt/evolve/` | `EvolveBundleExtractor` — unpacks the combined EWT+Evolve native bundle at runtime. |

### 1e. Elsewhere in the repo

Outside `ewt.api/src/main/java/dev/equo/ewt/`, everything is hand-written
by convention:

- `examples/` — user-facing sample apps.
- `annotation-processor/src/main/java/` — the Immutables extension that
  patches generated builders to extend `Widget`.
- `hot-reload-client/`, `hot-reload-plugin/` — Gradle plugin + JDWP client.

Test-side generated code — `ewt.api/src/test/java/dev/equo/ewt/support/variants/<Widget>Variants.java` — is written by `generator/lib/emit/variants_gen.dart` and consumed by the native render suite (see [`native-tests.md`](native-tests.md)). The registry aggregate `WidgetVariantsRegistry.java` is gitignored; the per-widget files are tracked.

## 2. Generator internals

The generator is a Dart program under `ewt/generator/`. Entry point is
`bin/generator.dart` (via `:generator:generator`); libraries live in
`lib/`. It reads Flutter's source through the Dart analyzer, and for each
class listed in `generation_index.dart` emits Java, C, and Dart artefacts.

### 2a. Emission pipeline

```
generation_index.dart
       │
       ▼
pre_generation.dart    ── writes generator/lib/subwidgets.dart
       │                     + widgets/lib/subwidgets.dart
       ▼                     (cached against pregeneration_index.dart.ts)
Types.getGen(class) ── dispatches to a shape class (see §2b)
       │
       ▼
AGen subclasses in emit/{java,c,dart,web}_emitter.dart
       │
       ▼
Outputs:
  - ewt.api/src/main/java/dev/equo/ewt/*.java   (per-widget Java)
  - EWT.java, WidgetConstructors.java           (aggregates)
  - widgets/src/{factories,objects,typedefs}.h  (C headers)
  - widgets/lib/factories_gen.dart              (Dart FFI factories)
  - widgets_web/lib/factories_web_gen.dart      (web decoders)
  - ewt.api/src/test/java/.../variants/*.java   (native-render variants)
```

Three FFI-bridge directions (Dart→C, C→Dart, JSON→Dart) share a template:
`emit/serialize/serialize_strategy.dart`, with three concrete strategies
in `emit/serialize/{to_c,to_dart,to_json}.dart`. If you need per-type
dispatch inside a strategy, extend the template — do NOT re-scatter
`if (t.isDartCoreString) …` branches across the three files.

### 2b. Shape catalog

Shapes live in `generator/lib/emit/shape/`. There are **9** today, split
into two groups by wiring:

**Java-side shapes** (dispatched from `Types.getGen` at `generator/lib/types.dart:36`) — 8 classes:

| Shape | File | Extends | Routed for | What it captures |
|---|---|---|---|---|
| `SubStateGen` | `sub_state_gen.dart` | `SubclassGen` | `SubState` | User-subclassable state class — Java-side `State` overrides. |
| `SubAnimatedStateGen` | `sub_animated_state_gen.dart` | `SubclassGen` | `SubAnimatedState` | Same as `SubStateGen` but wires the `AnimationController` lifecycle. |
| `TrackedSubWidgetGen` | `tracked_sub_widget_gen.dart` | `SubclassGen` | `SubStatefulWidget`, `SubStatelessWidget` | User-subclassable widget with an id-tracked registry so the Dart side can look the Java instance back up on callbacks. |
| `ImperativeControllerGen` | `imperative_controller_gen.dart` | `WidgetGen` | `AnimationController` | Widget whose "config" is itself an object with imperative methods (`.forward()`, `.stop()`). Wired via `ImperativeControllerGen.forAnimationController(...)`. Extend to `ScrollController` / `TabController` by adding another `for<Name>` factory + a case in `getGen`. |
| `ColorSwatchGen` | `color_swatch_gen.dart` | `ImmutableGen` | `MaterialColor` | Color type with numbered shade fields (`shade50` … `shade900`). Pre-resolves shades at emission and ships a custom web decoder. |
| `BuilderExpansionGen` | `builder_expansion_gen.dart` | `ImmutableGen` | `ListView` | `.builder` factory whose `itemBuilder`+`itemCount` is eager-expanded into a `List<Widget>` at serialize time. |
| `DragTargetGen` | `drag_target_gen.dart` | `ImmutableGen` | `DragTarget` | Builder callback with empty candidate/rejected lists for the static-child projection. |
| `AbstractFactoryHostGen` | `abstract_factory_host_gen.dart` | `WidgetGen` | `ImageFilter`, `ColorFilter` | Abstract Dart class whose named-factory ctors become Java `static` factories. Opts in via `isAbstractFactoryHost` returning true. |

**Fallbacks in `Types.getGen`** — if none of the switch cases match:

- Class with `@Immutable` (directly or via a supertype) and not
  `isAbstract` → `ImmutableGen` (the common path for value types like
  `EdgeInsets`, `BorderRadius`, `Duration`).
- Any other `ClassElement` → `WidgetGen` (default).
- `EnumElement` → `EnumGen`.
- `TypeParameterElement` → recurse on the bound.

So adding a Flutter value type that carries `@Immutable` is often
zero-code — the fallback handles it.

**Dart-side / pregeneration shape** — 1 class:

| Shape | File | Extends | Wired via | What it captures |
|---|---|---|---|---|
| `UniqueKeyDefaulterGen` | `unique_key_defaulter_gen.dart` | `DartSubclassGen` | `DartSubclassGen.forWidget` — NOT via `Types.getGen` | Forces a `UniqueKey()` default on `super.key` in the emitted Dart subclass ctor. Used for `StatefulWidget`-derived wrappers so two instances (both with `runtimeType == SubStatefulWidget`) don't share a null key and confuse Flutter's reconciliation. |

`DartSubclassGen` is a **fourth** base beyond the three Java-side bases
(`WidgetGen`, `ImmutableGen`, `SubclassGen`); it emits the Dart
`Sub<X>Widget<Y>` subclass in `widgets/lib/subwidgets.dart`. Extending it
is only needed when the pregeneration shape of a widget diverges from
the default subclass template.

**Note on the code's own docstring.** `Types.getGen` has a docstring at
`generator/lib/types.dart:30` listing "six shapes"; that comment is
stale — the actual switch has grown past what the docstring recites. If
you're refactoring `getGen`, update that docstring while you're there.

### 2c. Hooks on `WidgetGen`

Shapes override hooks on `WidgetGen` (or its `ImmutableGen` /
`SubclassGen` descendants) rather than embedding widget-name predicates
in emitter files. The main hooks, all defined in
`generator/lib/emit/base/widget_gen.dart`:

| Hook | Default | Overridden by | Purpose |
|---|---|---|---|
| `writeExtraJavaClassBody()` | no-op | `ImperativeControllerGen` | Extra Java members before the synthetic `build()` (e.g. web-command routing infrastructure for `AnimationController`). |
| `writeVoidMethodWebPrelude(factory)` | no-op | `ImperativeControllerGen` | Web-mode short-circuit / preroute before the FFM call on void-returning instance methods. |
| `tryWriteCustomInstanceMethodReturn(factory, returnType)` | `false` | shape-specific | Custom return marshaling for the non-void branch of an instance method wrapper. |
| `skipJavaSerializer(factory)` | `false` | `BuilderExpansionGen`, `DragTargetGen` | Skip emitting the Java-side serializer entry — used when a widget eager-expands at serialize time. |
| `dartFactoryCtorClass(node)` | `widgetClass` | rare | Which Dart class the factory should construct (differs from `widgetClass` when a wrapper factory targets a delegate). |
| `tryEmitCustomJavaSerializer(...)` | `false` | `ColorSwatchGen`, others | Emit a bespoke Java-side serializer body when the default won't do. |
| `emitExtraJavaSerializerFields(factoryName, objStClass)` | no-op | shape-specific | Extra fields on the emitted ObjSt class alongside the standard param fields. |
| `tryEmitCustomWebDecoder(factory, factoryName, node)` | `false` | `ColorSwatchGen`, `AbstractFactoryHostGen` | Bespoke web decoder in `factories_web_gen.dart`. |
| `skipWebFieldAccessor` | `false` | shape-specific | Suppress the web-side getter shims for a widget. |
| `isAbstractFactoryHost` | `false` | `AbstractFactoryHostGen` | Marks a widget as an abstract-factory host so factory ctors are exposed as Java `static` methods. Preferred over an emitter-level allowlist. |

When you need shape-specific behavior, prefer adding a new hook (with a
no-op default) plus overriding it in the shape class. Grepping the
emitters for `widgetClass ==` / `factoryName ==` should always return
zero code hits — a comment in `widget_gen.dart:85` documents the pattern.

## 3. Testing & invariants

### 3a. Snapshot test

`generator/test/snapshot_test.dart` freezes byte-for-byte references
for the aggregate outputs (the six files under `test/snapshots/`) that
would otherwise change with every widget added. Any generator change
that touches emission has to reconcile with these:

```bash
cd generator && dart test test/snapshot_test.dart
```

Three outcomes:

- **Green.** Change preserves byte-for-byte output. Commit.
- **Red on files related to your change.** Expected. Refresh with
  `dart run tool/update_snapshots.dart`, verify diff, commit generator
  change and snapshot refresh **in the same commit**.
- **Red on files unrelated to your change.** Something else regressed.
  Do NOT refresh — investigate. Common causes: your predicate matched
  a widget you didn't expect; a hook default drifted; dispatch order in
  `getGen` matters and a case moved above/below where it needed to be.

Widgets added to `generation_index.dart` intentionally change the
per-widget Java outputs and the aggregate files (`factories_gen.dart`,
`factories.h`, etc.). That's expected — the per-widget diffs live in
git for review.

### 3b. `--strict` audit

```bash
cd generator && rm -f build/pregeneration_index.dart.ts && \
  dart run bin/generator.dart --strict
```

Exit code 1 means at least one `warn:` fired during generation. Every
warn is a widget dropped or a type unsupported. Read stderr to see
which, then either close the gap in the generator or comment the
widget out of `generation_index.dart` with a reason.

Warnings must be emitted via `warn(...)` from `lib/diagnostics.dart` —
not `print()` / `stderr.writeln()` directly — so `--strict` sees them
and CI can gate on them.

### 3c. Anti-patterns

Enforced by convention, not by tooling:

- **`widgetClass == 'X'`** or **`factoryName == 'X'`** inside an
  emitter file. Push to `Types.getGen` + a shape override.
- **Duplicating kind dispatch across serialize strategies.** All three
  (`to_c.dart`, `to_dart.dart`, `to_json.dart`) share
  `dispatchInterface` in `serialize_strategy.dart`. If you're writing
  `if (t.isDartCoreString) … if (t.isDartCoreBool) …` in a strategy
  file, you're in the wrong layer.
- **Adding structural predicates to `getGen`** (`c.allSupertypes.any(...)`)
  without auditing every widget in `generation_index.dart` that would
  newly match. Silent re-routing is how `MaterialAccentColor` slipped
  into `ColorSwatchGen` — see the historical F7.5 note (removed with
  the doc rewrite; the lesson stands).
- **Adding an unused parameter "for future".** `_inlinePrivateRefs` in
  `params.dart` deliberately does NOT take a `visited` set today
  because it's not recursive. Add it when you make it recursive, not
  before — dead code muddles the invariant. There is a `// If this
  ever becomes recursive` comment there marking the trigger.
- **Editing generated files.** Per-widget `.java` files under
  `ewt.api/src/main/java/dev/equo/ewt/` are committed (as baselines
  for review) but they are outputs, not sources. Edit the generator.
- **Hardcoding widget names in helpers.** If a helper needs
  widget-specific behaviour, expose a hook on `WidgetGen` (see §2c).
- **Referencing Flutter's private (`_`-prefixed) classes from emitted
  code.** Dart's library-private rule makes `_PrivateClass` inaccessible
  from `widgets/lib/factories_gen.dart`, so any generated Dart that
  names such a class fails to compile. `Types.addRequiredType` skips
  private types entirely, and `WidgetGen.writeHeaders` walks past
  private intermediate supertypes to the first public ancestor when
  emitting the Java `extends` clause. Do not re-introduce a code path
  that queues a private type for emission — grep for
  `element.name.startsWith('_')` before adding a new discovery hook.

## 4. Deferred widgets

Widgets whose Dart constructor the generator cannot currently marshal.
Each entry names the specific generator gap and — where known — the
concrete work needed to close it.

### `Dismissible`

**Why:** requires `Key key` as a positional-required parameter. The
generator has no strategy for synthesizing a `Key` (Flutter uses `Key`
identity for reconciliation, and the Java side has no equivalent).

**To enable:** teach the emit path in `generator/lib/gen.dart` to
auto-synthesize a `ValueKey<int>` (using the widget's `id`) whenever a
required `Key` param is seen. Same pattern the `DefaultTabController`
already uses for its `TabController`.

### `TweenAnimationBuilder`

**Why:** requires `Tween<T>` (abstract generic value type). The
generator can register concrete `Tween` implementations but not the
abstract with a free type parameter.

**To enable:** add a marshaling handler for `Tween<T>` — probably as a
value type carrying `begin`/`end` of the bound type, similar to how
`Curve` is handled today.

### `DropdownMenu<T>`

`DropdownButton<T>` and `DropdownMenuItem<T>` are **now supported** —
the private-supertype skip (see §3c anti-patterns and `Types.addRequiredType`
+ `WidgetGen.writeHeaders`) landed and unblocked them together with
`BackButton` / `CloseButton` / `DrawerButton` / `EndDrawerButton`,
which had the same shape (concrete widget extending a Flutter
implementation-private class).

`DropdownMenu<T>` is still deferred for a different reason:
`filterCallback` and `searchCallback` pass `List<DropdownMenuEntry<T>>`
through the FFI boundary, and the current callback path doesn't marshal
that shape.

**To enable:** extend `paramValueDtoC` in `generator/lib/gen.dart` so
callbacks whose parameters are `List<T>` of an ObjSt-emitted type can
round-trip. Same infrastructure would unblock any future widget with a
callback taking a widget list.

### `Autocomplete<T>`

**Why:** `optionsBuilder` returns `FutureOr<Iterable<T>>`. Neither
`FutureOr<...>` nor `Iterable<...>`-returning callbacks are supported by
the generator's Dart-side callback wrapper (`paramValueDtoC` in
`gen.dart`).

**To enable:** register `FutureOr<T>` as `T` on the Dart side
(unwrapping is safe since Java always returns synchronously through the
FFI boundary), and add an `Iterable<T>` → `List<T>` alias in
`types.dart` for return-type marshaling.

### `SearchAnchor`

**Why:** `builder`, `suggestionsBuilder`, and `viewBuilder` all take a
`SearchController` (an EWT-managed controller class). `SearchController`
is not currently ObjSt-emitted for its widget-callback surface, so the
callback-side wrappers can't reconstruct the Java object from a plain
int id.

**To enable:** either register `SearchController` as an ObjSt-emitted
type (matching how `TabController` is handled), or expose a hand-written
Java adapter that Java code passes into the builder.

### `PaginatedDataTable`

**Why:** constructor requires `DataTableSource source`, an abstract
Dart class. Flutter users normally subclass `DataTableSource` in Dart
to supply `rowCount`, `getRow(int)`, and `isRowCountApproximate`. From
Java there's no path to subclass a Dart class.

**To enable:** ship a Dart-side `EwtDataTableSource` adapter class
(under `widgets/lib/`) that implements `DataTableSource` by delegating
each method to a Java callback (`Function<Integer, DataRowI>`,
`Supplier<Integer>`), then register it in the type registry so
`PaginatedDataTable.source` picks it up. Same DataTable factory covers
the non-paginated case in the meantime.

### `List<double>` / `List<int>` parameters (any widget)

**Why:** primitive-numeric lists have no length prefix in the current
FFI marshaling protocol — `paramValueDtoC` can't unmarshal them back
into a Dart `List` on the callback path.

**To enable:** extend the ArrayC struct with a length field for
primitive types, or box on the Java side to `List<Double>` / `List<Integer>`
before crossing the boundary.

### Callbacks with 6+ parameters

**Why:** callback dispatch tops out at `PentaFunction` / `PentaConsumer`
(5 args). Anything above needs new arity classes in
`ewt.api/src/main/java/dev/equo/ewt/util/` and matching switch entries
in `FunctionHandler`.

**Currently no supported Flutter widget hits this** — the ceiling
matches the widest signature in the stable Flutter API (`Hero.flightShuttleBuilder`,
5 args) — but note this shape is not extensible today.

## 5. When to regenerate

Full pipeline:
```bash
rm -f generator/build/pregeneration_index.dart.ts   # only needed if generation_index.dart changed
JAVA_HOME=~/bin/jdk-22 ./gradlew :generator:generator
JAVA_HOME=~/bin/jdk-22 ./gradlew :ewt.api:jar -PuseLocal=true
```

Both tasks have `finalizedBy` wiring that runs `ffigen` + `jextract`, so
never invoke those sub-tasks directly.

After adding entries to `generation_index.dart`, also refresh coverage:
```bash
cd generator && dart tool/coverage_audit.dart
```

If you edit anything in the hand-written support section (1c / 1d),
re-run the generator afterwards — the generator inspects the current
Java signatures via annotation processing and its output can shift.
