# EWT generator structure

Companion to [`coverage.md`](coverage.md). Where `coverage.md` answers _which
Flutter widgets are supported_, this file answers _how the Java surface is
laid out_ and _which shapes the generator still can't handle_.

## 1. Hand-written vs. generated Java

Every `.java` file in `ewt.api/src/main/java/dev/equo/ewt/` and its
subpackages falls into one of four buckets.

### 1a. Generated on every `:generator:generator` run

**Path:** `ewt.api/src/main/java/dev/equo/ewt/*.java` (top-level only).

For each entry in `generator/lib/generation_index.dart`, the generator emits:

- `<Widget>.java` — concrete class + Immutables `@Builder.Factory`.
- `<Widget>I.java` — the builder interface consumed by other generated
  widgets' typed params.

Also generated top-level: enums declared inside Flutter widget libraries
(`BlendMode.java`, `Clip.java`, `DatePickerEntryMode.java`, …).

Two aggregate files are re-written each run:

- `EWT.java` — the static-factory facade (`EWT.DataTable(...)`,
  `EWT.showDatePicker(...)`, …).
- `WidgetConstructors.java` — the FFM dispatch table Java calls into.

### 1b. Generated by `:ewt.api:jextract`

**Path:** `ewt.api/src/main/java/dev/equo/ewt/ffm/` (entire subpackage).

**Gitignored** (see `.gitignore` line for `ewt.api/src/main/java/dev/equo/ewt/ffm/`).
Jextract produces one Java class per C struct / function pointer declared in
`widgets/src/Starter.h` (which is itself regenerated). Never edit — these
files are recreated from scratch on each build.

### 1c. Hand-written support (top-level `dev/equo/ewt/`)

These files are checked in and never overwritten by the generator. They
implement the base classes and mixins the generated widgets depend on:

| File | Role |
|---|---|
| `App.java` | Entry point (`App.runApp(...)`), native library loader, FFM arena. |
| `NativeObj.java` | Opaque native handle — the `int id` that survives the Java↔Dart boundary. Provides `NativeObj.Base` used by every `EWT.*` value type. |
| `Widget.java`, `StatefulWidget.java`, `StatelessWidget.java`, `State.java` | Flutter-analog base classes for user code. |
| `SubStatefulWidget.java`, `SubStatelessWidget.java`, `SubState.java`, `SubAnimatedState.java` | EWT subclass-in-Java pattern — the four classes users extend to build custom widgets with Java-side overrides. |
| `SubclassedInJava.java` | Marker interface consumed by the generator's `SubclassGen` code path (see the `_ewtSubclassNames` allowlist in `generator/lib/types.dart`). |
| `BuildContext.java` | Small interface wrapper around the generated `BuildContextI`. |
| `WidgetConstructorsBase.java` | Base class extended by the generated `WidgetConstructors` — holds the `factories` field and other cross-widget statics. |
| `SerializingWidgetConstructors.java` | Web-transport equivalent of `WidgetConstructors`; serializes widget calls into a JSON message the web runtime replays. |
| `EwtCapture.java`, `EwtWebCapture.java`, `EwtWebState.java`, `EWTStyle.java` | Web-integration helpers used from the web transport path. |
| `NativeLibLoader.java` | Picks the correct native library set per-OS / per-mode (standalone vs. Evolve attach). |
| `Colors.java`, `Curves.java`, `Icons.java`, `CupertinoIcons.java`, `Durations.java` | Static constant holders — the generator emits these as pass-through wrappers, but the constant tables themselves are curated. |

If you touch anything in this list, remember to regenerate afterwards
because the generator's output depends on their signatures being stable.

### 1d. Hand-written subpackages

Fully hand-written; never touched by the generator.

| Package | Contents |
|---|---|
| `dev/equo/ewt/util/` | `Tri*`/`Quad*`/`Penta*` `Function`/`Consumer` interfaces — arity extensions beyond `java.util.function.BiFunction`. Consumed by generated code (e.g., `PentaFunction` is what `Hero.flightShuttleBuilder` compiles to). |
| `dev/equo/ewt/internal/` | `EmbedBridge` (EWT↔Evolve same-surface integration), `HotReloadRoot` (JDWP-triggered `reassembleApplication` wrapper). |
| `dev/equo/ewt/web/` | Web-transport plumbing: `EwtWebTransport`, `EwtNode`, `EwtNodeJson`, `EwtDiff`, `Patch`, `SetParamsOp`. Reads/writes the JSON diff protocol used by `widgets_web`. |
| `dev/equo/ewt/evolve/` | `EvolveBundleExtractor` — unpacks the combined EWT+Evolve native bundle at runtime. |

### 1e. Elsewhere in the repo

Outside `ewt.api/src/main/java/dev/equo/ewt/`, everything is hand-written
by convention:

- `examples/` — user-facing sample apps.
- `annotation-processor/src/main/java/` — the Immutables extension that
  patches generated builders to extend `Widget`.
- `hot-reload-client/`, `hot-reload-plugin/` — Gradle plugin + JDWP client.

## 2. Deferred widgets

Widgets whose Dart constructor the generator cannot currently marshal.
Each entry names the specific generator gap and — where known — the
concrete work needed to close it.

### `Dismissible`

**Why:** requires `Key key` as a positional-required parameter. The
generator has no strategy for synthesizing a `Key` (Flutter uses `Key`
identity for reconciliation, and the Java side has no equivalent).

**To enable:** teach the emit path in `generator/lib/gen.dart` to
auto-synthesize a `ValueKey<int>` (using the widget's `id`) whenever a
required `Key` param is seen. Same pattern the `DefaultTabController`
already uses for its `TabController`.

### `TweenAnimationBuilder`

**Why:** requires `Tween<T>` (abstract generic value type). The
generator can register concrete `Tween` implementations but not the
abstract with a free type parameter.

**To enable:** add a marshaling handler for `Tween<T>` — probably as a
value type carrying `begin`/`end` of the bound type, similar to how
`Curve` is handled today.

### `DropdownButton<T>`, `DropdownMenuItem<T>`, `DropdownMenu<T>`

**Why:** `DropdownMenuItem<T>` in Flutter extends the **private**
`_DropdownMenuItemContainer`. When the generator processes
`DropdownMenuItem` it walks the type hierarchy and pulls
`_DropdownMenuItemContainer` in as a subwidget, then emits FFI setup
against a private symbol — both `f._DropdownMenuItemContainer._Dropdown…`
field access and `ffi.Struct.create()` on a private class fail to
compile in the generated `factories_gen.dart`.

`DropdownMenu<T>` has a separate landmine: `filterCallback` /
`searchCallback` pass `List<DropdownMenuEntry<T>>` through the FFI
boundary, and the current callback path doesn't marshal that shape.

**To enable:** teach the subwidget-discovery loop in
`generator/lib/gen.dart` to skip supertypes whose Dart name begins with
`_`. Then re-enable `DropdownButton` and `DropdownMenuItem`.
`DropdownMenu` needs the additional callback work.

### `Autocomplete<T>`

**Why:** `optionsBuilder` returns `FutureOr<Iterable<T>>`. Neither
`FutureOr<...>` nor `Iterable<...>`-returning callbacks are supported by
the generator's Dart-side callback wrapper (`paramValueDtoC` in
`gen.dart`).

**To enable:** register `FutureOr<T>` as `T` on the Dart side
(unwrapping is safe since Java always returns synchronously through the
FFI boundary), and add an `Iterable<T>` → `List<T>` alias in
`types.dart` for return-type marshaling.

### `SearchAnchor`

**Why:** `builder`, `suggestionsBuilder`, and `viewBuilder` all take a
`SearchController` (an EWT-managed controller class). `SearchController`
is not currently ObjSt-emitted for its widget-callback surface, so the
callback-side wrappers can't reconstruct the Java object from a plain
int id.

**To enable:** either register `SearchController` as an ObjSt-emitted
type (matching how `TabController` is handled), or expose a hand-written
Java adapter that Java code passes into the builder.

### `PaginatedDataTable`

**Why:** constructor requires `DataTableSource source`, an abstract
Dart class. Flutter users normally subclass `DataTableSource` in Dart
to supply `rowCount`, `getRow(int)`, and `isRowCountApproximate`. From
Java there's no path to subclass a Dart class.

**To enable:** ship a Dart-side `EwtDataTableSource` adapter class
(under `widgets/lib/`) that implements `DataTableSource` by delegating
each method to a Java callback (`Function<Integer, DataRowI>`,
`Supplier<Integer>`), then register it in the type registry so
`PaginatedDataTable.source` picks it up. Same DataTable factory covers
the non-paginated case in the meantime.

### `List<double>` / `List<int>` parameters (any widget)

**Why:** primitive-numeric lists have no length prefix in the current
FFI marshaling protocol — `paramValueDtoC` can't unmarshal them back
into a Dart `List` on the callback path.

**To enable:** extend the ArrayC struct with a length field for
primitive types, or box on the Java side to `List<Double>` / `List<Integer>`
before crossing the boundary.

### Callbacks with 6+ parameters

**Why:** callback dispatch tops out at `PentaFunction` / `PentaConsumer`
(5 args). Anything above needs new arity classes in
`ewt.api/src/main/java/dev/equo/ewt/util/` and matching switch entries
in `FunctionHandler`.

**Currently no supported Flutter widget hits this** — the ceiling
matches the widest signature in the stable Flutter API (`Hero.flightShuttleBuilder`,
5 args) — but note this shape is not extensible today.

## 3. When to regenerate

Full pipeline:
```bash
rm -f generator/build/pregeneration_index.dart.ts   # only needed if generation_index.dart changed
JAVA_HOME=~/bin/jdk-22 ./gradlew :generator:generator
JAVA_HOME=~/bin/jdk-22 ./gradlew :ewt.api:jar -PuseLocal=true
```

Both tasks have `finalizedBy` wiring that runs `ffigen` + `jextract`, so
never invoke those sub-tasks directly.

After adding entries to `generation_index.dart`, also refresh coverage:
```bash
cd generator && dart tool/coverage_audit.dart
```

If you edit anything in the hand-written support section (1c / 1d),
re-run the generator afterwards — the generator inspects the current
Java signatures via annotation processing and its output can shift.
